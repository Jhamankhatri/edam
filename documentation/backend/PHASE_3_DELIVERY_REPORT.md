### The failures the tests found

Four failures were defects rather than wrong expectations:

1. **`GET /auth/csrf` issued a token in the body and wrote no cookie** — a latent Phase 1 bug. Spring Security 6
   defers token creation and only the filter's dereference on an unsafe method saves the cookie, so an SPA
   bootstrapping with that endpoint had nothing to send on its first write. Fixed.
2. **A duplicate approval returned 422, not the 409 the test expected.** The system was right; the test assumed
   the wrong code and now documents why a retry would not help.
3. **`submit` refused a draft-shaped payload**, correctly — the Phase 2 validator requires an allocation and a
   quotation before submission. The new fixture was building a draft payload.
4. **An "outside their data scope" test was not actually outside it** — the approver shared the request's
   department, so the register legitimately served the row and the assertion proved nothing.

Two failures were the schema refusing a test's invented reference: a `ROLE` designation naming a role that does
not exist, and an `EXPENSE_COMMITTEE` step naming a level that does not exist. Both foreign keys rejected them,
which is the constraint doing its job. The tests now create a real role nobody holds and a real level nobody
sits on — the condition that actually matters.

## 7. Versioning evidence

The requirement is that a published revision is immutable and that in-flight requests keep the version they
started under. Evidence, from `WorkflowConfigurationApiTest` and `SubmissionIntegrationTest`:

| Property | Test | What it asserts |
|---|---|---|
| Publication stamps and activates | `publishStampsRevision` | Status, timestamp, publisher, and that `requirePublishedForRequestType` returns it |
| A published revision is never rewritten | `publishedRevisionIsImmutable` | Authoring again opens **v2**; v1 remains `PUBLISHED` with its original two approvers, read back through the service |
| Superseded revisions are kept | `secondPublicationRetiresFirst` | v1 becomes `RETIRED`, not deleted; `findPublished` returns v2 |
| One editable revision at a time | `onlyOneDraftAtATime` | Authoring twice rewrites the same revision; exactly one editable version exists |
| Invalid workflows cannot publish | `noApproverRefused`, `danglingApproverReferenceRefused` | Publication refuses and the revision stays `DRAFT` |
| A past effective date is refused | `pastEffectiveDateRefused` | — |
| Retirement leaves the type unsubmittable | `retiredLeavesNothingToStart` | Fails closed rather than falling back |
| **In-flight pinning** | `inFlightKeepsItsVersion` | Publishes v2 while a request is in approval; the instance still reports v1, **and** the published pointer is asserted to have moved, so the check is not vacuous |
| New submissions use the new revision | `newSubmissionUsesNewRevision` | The next submission pins v2 |

### What this phase deliberately did not do

* **No frontend work**, as instructed.
* **No faked workflow instances or placeholder tasks.** Every test publishes a chain through the real
  configuration service and submits through the real request service.
* **No hardcoded approval ladder, bank department names, approval levels, or CEO/CFO rules in Java.** OPEX and
  CAPEX differ by which request type a definition is bound to, not by an `if`.
* **No duplicate workflow tables, state models or parallel approval engines.** Phase 3 extends the Phase 2 engine
  and changes it in one place only: `resumeAtFirstStep`, so a reverted request re-enters its original instance
  rather than starting a second one on the current revision.
* **No weakened database constraints.** V17 adds three and weakens none.
