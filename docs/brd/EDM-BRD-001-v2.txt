1. Executive Summary

The Expense Delegation Matrix (EDM) is a configuration-driven expense request, delegation and approval platform for Head Office Operating Expenditure (OPEX) and Capital Expenditure (CAPEX). Administrators configure categories, sub-categories, delegation rules, recommending authorities, Expense Committee (EC) levels, currencies and approval limits. Requesters then submit expenses; the system determines the approval route from the configured rules rather than asking the requester to choose approvers.

The reference implementation is an ASP.NET Web Forms application backed by Microsoft SQL Server stored procedures and shared Albaraka/ApplicationPanel master data. The target product will expose versioned REST APIs from a Java Spring Boot backend using PostgreSQL. The user interface will be a separately developed React application. The backend must expose institution branding, theme tokens, navigation/feature configuration, workflow definitions, business rules, permissions and notification-template configuration through secured APIs so that the later React implementation does not require backend contract redesign. The rebuild is intended to reduce database-procedure coupling, improve maintainability and make the product reusable for multiple client institutions.

The reference document describes 13 functional modules, OPEX and CAPEX form field maps, 46 OPEX save parameters, 57 CAPEX save parameters, approval workflows, reporting, configuration audit trails and several known gaps. The BRD treats those findings as the functional baseline and separately labels target-product proposals.

2. Business Context and Problem Statement

2.1 Current Situation

The existing EDM is implemented in .NET / ASP.NET Web Forms and Microsoft SQL Server.

A significant amount of behaviour is implemented in stored procedures and direct database queries, making business flow difficult to maintain and evolve in the application layer.

The current implementation depends on shared ApplicationPanel user, department and branch data.

The supplied reference records inconsistent/legacy table usage, unclear workflow combinations, incomplete role-based access checks and undocumented deployment/NFR details.

The current application is reported by the requester as unstable and difficult to maintain; this operational assessment is requester-provided context, not a measured finding in the reference specification.

2.2 Business Problem

The business needs a stable, auditable and configurable workflow product that can enforce expense delegation consistently across OPEX and CAPEX without rebuilding client-specific logic for each bank or institution.

2.3 Desired Business Outcome

A maintainable application-layer workflow engine with database persistence and integrity constraints.

Central administration of approval routing and financial thresholds.

Consistent request, approval, revert, resubmission and reporting experiences.

Tenant/client-specific branding and business configuration without code changes for ordinary configuration differences.

Clear traceability for every request, approval action, configuration change and notification.

6.1 Navigation Behaviour

OPEX submission returns the user to the OPEX register.

CAPEX submission returns the user to the CAPEX register.

Register rows open the relevant approval/view page.

A reverted request opens in editable mode for its creator in My Request or designated recipient in My Approvals; other users see the read-only approval view.

Reporting detail links open the relevant OPEX or CAPEX approval/detail page.

Register default date filter is the previous 30 days through today.

7. End-to-End Business Processes

7.1 OPEX Request Lifecycle

Requester opens OPEX form; system pre-fills requester, department, date and reference.

Requester enters expense classification, vendor, currency, amounts, allocations, invoices, business flags and justification.

Requester completes required-document checklist and uploads supporting documents.

System validates required values, invoice/approval amount equality, positive amount, justification and conditional attachments.

System saves request and resolves the approval route from active configuration.

Requester tracks the request in My Request; approvers see assigned items in My Approvals.

If returned, the creator or designated revert recipient corrects and resubmits under the applicable workflow path.

7.2 CAPEX Request Lifecycle

Eligible department user opens CAPEX form; new-request access is limited to Admin, Information Technology and Digital in the reference implementation.

Requester enters category/sub-category, vendor, currency, amount, tax, payment terms, finance fields, asset-book allocations, item-wise details and budget information.

System validates invoice total, approval amount and charge total; requires item-wise details and valid warranty date.

Requester completes checklist and attaches required documents.

System saves request and routes it through the configured CAPEX workflow.

If routing fails after save, the legacy application deletes the request; the new design must instead use an atomic transaction so incomplete requests are not committed. (Target proposal)

Returned CAPEX requests can be corrected and resubmitted when eligible.

7.3 Approval Processing

Approver opens an assigned request; request details are read-only.

System verifies that the user has a pending approval at the current workflow step and has not already acted at that step.

Action panel is displayed only when assignment, status and workflow rules permit it.

Approver selects an available action. Remarks are required for approve, reject and revert; forward requires a recipient and remarks.

System records the action, updates workflow progress/status and triggers applicable email notification.

EC progress is calculated using the configured quorum and any required CEO/CFO participation.

7.4 Revert and Resubmission

A revert action requires remarks/comments.

An EC-stage revert returns the request to the last Phase-1 approver.

The requester sees the reverted request in My Request and can edit it.

In My Approvals, only the designated revert recipient receives editable access; other approvers receive read-only view.

Selective revert to a chosen previous approver is supported for eligible requests; eligibility criteria remain an open decision.

Workflow resume and Phase-2 resubmission are separate documented operations in the legacy implementation; the exact target state machine must be approved.

Approval pages display request details read-only, allocations, checklist, attachments and milestone/history.

10. Approval and Delegation Framework

10.1 Documented High-Level Route

The documented normal route is: Request Submission → Department Head / Unit Head (Phase 1) → Recommending Authority (where configured) → Expense Committee level(s) (Phase 2), with CEO and/or CFO participation when configured.

10.2 Department Head Limit

Approval amount at or below the configured General Delegation limit routes to the Department Head only (Phase 1).

Approval amount above the limit proceeds through Phase 1 and then the configured later approval route.

Legacy helper default is PKR 20,000 when no configured limit is available.

10.3 EC Levels and Quorum

EC levels have configured amount ranges, selected members, required EC member count and minimum approval count.

The reference narrative describes Levels 1–3 as descending approval intensity; exact amount boundaries and relationship to configurable EC levels are not verified.

Required CEO/CFO participation is configured at EC level; CEO cannot reject. CFO action restrictions need confirmation.

10.4 Standalone Approvals

Standalone CEO and Head of Admin & GST (HOD) routing, and CEO/CFO standalone approval limits, are described in the product narrative. Their precise sequence, limits, interaction with EC levels and action permissions are not sufficiently defined. These must not be implemented by assumption.

10.5 Approval State Machine

The source names Pending, Approve, Reject, Revert and Forward; CAPEX also uses Submitted. The complete state machine, terminal statuses, allowed transitions, cancellation/deletion policy and concurrency behaviour are not supplied. A formally approved state-transition matrix is a release prerequisite.

13. Security and Access Control

The reference implementation has authentication/session checks in many pages but does not establish a complete role-based permission model. Some configuration pages have no role check in page source. The reporting module hard-codes every signed-in user as Finance_Admin and disables intended role checks. This is a material control gap.

13.1 Target Requirements

Require authenticated access to all application pages and server endpoints.

Enforce authorization on the server for every operation; hiding a frontend button is not an authorization control.

Define institution-configurable roles and permissions for request creation, viewing, approval, configuration, reporting, audit viewing and export.

Enforce record-level access: requester ownership, current workflow assignment, designated revert recipient, department restrictions and tenant boundary.

Prevent duplicate or replayed approval actions through transactional state checks.

Protect vendor CNIC, NTN, STRN, contact number and address according to the client's security/privacy policy.

Never log passwords, authentication tokens, full sensitive identifiers or document contents.

Define session timeout, password/SSO policy, encryption, retention and backup requirements with the client security team.

These security controls are target proposals and must be approved by the bank/client security stakeholders; the reference document does not provide encryption, masking, retention or certification requirements.

Abstract document-storage service; storage provider is configurable after client decision.

Notifications

Email adapter with templates, outbox/retry mechanism and configurable SMTP/provider settings.

Operations

Externalized environment configuration, secrets management, health/metrics/logging and repeatable deployment.

15.2 Architecture Principles

Keep business rules and workflow decisions in Java domain/application services; use PostgreSQL for persistence, relational integrity, indexes and transactional guarantees.

Do not reproduce the legacy stored-procedure architecture one-for-one. Reimplement the business behaviour, not the old technical coupling.

Use a modular monolith as the initial deployment shape unless scale or organizational boundaries justify service decomposition.

Separate OPEX and CAPEX domain-specific fields while reusing common request lifecycle, attachment, allocation, approval, audit and reporting capabilities where semantics match.

Keep client-specific differences in configuration/strategy/adapter layers, not scattered if/else conditions or hard-coded constants.

Use database migration scripts (e.g. versioned migrations) as the controlled schema change mechanism.

Use DTO validation at request boundaries and domain validation in services; never trust client-side validation alone.

Use transactional boundaries around request submission, route creation, approval action, revert and resubmission.

21. Product Vision, Institution Model and Tenant Administration

EDAM shall operate as one reusable product instance or product deployment serving one or more financial institutions, according to the approved tenant-isolation model. Each institution must be configurable without forking the application or introducing institution-specific business logic.

21.1 Institution Management

The platform shall allow an authorized platform administrator to create, view, update, activate, suspend and deactivate institution records.

Each institution shall have a unique immutable institution identifier, institution code, legal/display name, status, time zone, locale, default currency, date/number formats and contact metadata.

Institution onboarding shall support initial administrator assignment, configuration defaults and a controlled activation process.

Institution-specific settings shall be isolated from other institutions and all institution-owned records shall be associated with an institution context.

The platform shall support institution-specific logo, favicon, login branding, product name/label, theme palette, typography tokens where supported, email branding and document/report branding.

Administrators shall be able to configure enabled modules/features per institution; disabled features must be unavailable through both UI configuration and backend authorization.

Institution settings shall support draft/preview/publish where a setting materially changes the user experience; changes shall be audited.

Institution administrators shall only manage their own institution. Cross-institution administration shall be restricted to explicitly authorized platform-level roles.

The system shall prevent cross-tenant record access even if a caller manipulates identifiers or API requests.

21.2 Tenant Isolation and Data Segregation

OPEN DECISION: choose shared database/shared schema with tenant_id, schema-per-tenant, or database-per-tenant after security, regulatory, operations, backup/restore, reporting and cost review. The selected model must be documented in an Architecture Decision Record before tenant-aware business data implementation.

Tenant context shall be derived from a trusted authenticated identity/session/token claim or a validated server-side mapping; never trust a tenant_id supplied only by an arbitrary request body/header.

Tenant context must be applied consistently to reads, writes, exports, background jobs, notifications, file access, caches and audit queries.

Database constraints and/or repository/service safeguards shall prevent tenant ownership mismatches.

Automated negative tests shall prove that users in Institution A cannot read, update, delete, approve, export or download Institution B data.

Platform support access shall be privileged, explicitly granted, time-bound where feasible, and audited.

Backups, retention, restore, data export and deletion must respect the selected tenant isolation strategy.

Authorized administrators shall create, edit, activate, deactivate and assign custom roles within their permitted institution scope.

The product shall provide predefined role templates for common personas (platform administrator, institution administrator, requester, department head, recommending authority, committee member, finance reviewer, auditor and read-only user) while allowing controlled customization.

The backend shall evaluate: authenticated identity + active institution membership + assigned role permissions + record ownership/scope + workflow assignment/current step + resource status. 24. Configurable Workflow Engine and Workflow Designer

The target product shall provide a backend workflow capability that supports the existing OPEX/CAPEX approval behavior and future institution-specific approval paths. A future React-based workflow designer shall configure the engine through APIs; the workflow engine must not depend on UI implementation details.

24.1 Workflow Definition Capabilities

Configure workflows by institution, expense nature (OPEX/CAPEX), category, subcategory, amount range, department, budget status and other approved business dimensions.

Support sequential and parallel approval stages, configurable approver roles/users/designations, required participants, minimum approval counts/quorum and optional participants.

Support amount bands with non-overlapping range validation, inclusive/exclusive boundary definition and explicit currency basis.

Support routing to department head, recommending authority, Expense Committee, CEO, CFO and other institution-configured approver groups.

Support conditions, branching, fallback approvers and explicit handling when no eligible approver is found.

Support approve, reject, forward, revert, return for correction, resubmit and cancellation only where approved by the workflow policy.

Support escalation rules and reminders based on configured business calendars and SLA timers as a configurable enhancement.

Support effective-from/effective-to dates, draft/published status, workflow versioning and retirement of old versions.

A request shall retain the exact workflow version and resolved approval path used at submission; later configuration changes shall not silently rewrite an in-flight request.

Support workflow validation and simulation using sample request attributes before publication.

Prevent publishing invalid workflows, including unreachable steps, missing approvers, conflicting ranges, circular routes and impossible quorum requirements.

Support controlled workflow cloning from a template to another institution, with explicit review and publish in the target institution.

24.2 Workflow Designer Contract

The React workflow designer is a later frontend deliverable. Backend APIs shall support retrieval, draft creation, update, validation, simulation, publish, version history, compare and rollback/restore of eligible prior definitions.

24.3 Workflow Execution and Resilience

Workflow execution shall be transactional with the request state and approval task creation.

Duplicate submissions/actions shall be protected through idempotency or equivalent duplicate-action controls.

Concurrent approvals shall be handled safely; the same pending task must not be completed twice.

Every transition shall record actor, action, timestamp, remarks where required, previous state, new state, workflow version and correlation ID.

Background reminders/escalations shall be idempotent and observable.

Workflow failures shall not leave a request in an ambiguous partially-updated state.

25. Configurable Business Rules and Policy Administration

Business rules shall be externalized from client-specific source code where they are intended to vary by institution. Core invariant rules and security controls remain enforced in application code and database constraints.

Provide institution-scoped rule sets for request validation, amount thresholds, category eligibility, CAPEX department eligibility, budget policy, required documents and approval routing conditions.

Support rule name, description, priority, condition, outcome/action, effective dates, status, version, creator, reviewer and publication history.

Provide a constrained, documented rule expression model or decision-table model; do not execute arbitrary Java, JavaScript, SQL or uploaded code from administrators.

Validate rule syntax, types, references and conflicting priorities before publication.

Support test/simulation with sample input and explain which rules matched and why.

Define deterministic rule precedence and conflict handling.

OPEN DECISION: identify which current OPEX/CAPEX validation rules are institution-configurable versus mandatory product invariants. No bank-specific policy may override tenant isolation, authorization, audit integrity or other platform security controls.

28.4 Secret and Credential Protection

BANK-GRADE SECURITY REQUIREMENT: SMTP/API credentials, signing secrets, OAuth client secrets, storage keys and integration credentials are sensitive secrets, not ordinary configuration values.

Preferred approach: store secrets in a managed secrets vault or cloud KMS-backed secret manager, with the application database holding only a secret reference and non-sensitive metadata.

If a managed vault is unavailable, use envelope encryption with a strong data-encryption key protected by a key-encryption key held outside the database and outside source control (for example, a KMS/HSM or controlled deployment secret).

Never store secrets in plaintext in PostgreSQL, application properties committed to Git, frontend code, browser storage, logs, audit diffs, exception messages or exported configuration.

The application must never provide an API to retrieve a saved secret in plaintext. UI should show only configured/not configured, masked metadata and rotation status.

Restrict secret create/rotate/delete operations to narrowly authorized administrators; apply maker-checker approval where the bank requires it.

Audit who changed secret metadata or rotated a credential without recording the secret value.

Support key rotation, secret rotation, revocation, least-privilege access and emergency disable procedures.

Separate development, test, staging and production secrets and prevent cross-environment reuse.

Document backup/restore implications: encrypted secret recovery requires the approved key-management recovery procedure.

OPEN DECISION: each deployment/bank must approve the secret manager, KMS/HSM, key ownership, rotation interval, recovery process and whether email credentials are institution-managed or centrally managed.

29. API-First Backend and Separate React Frontend Requirements

The backend shall be developed and completed before the React frontend. The backend must be frontend-independent and expose all business capabilities through documented REST APIs. No JSP, Thymeleaf or server-rendered application pages are part of the target product UI.

29.1 API Contract Requirements

Use versioned REST API paths and JSON request/response contracts; versioning policy and compatibility rules shall be documented.

Publish an OpenAPI specification for every released API and keep it aligned with implementation.

Use consistent response envelopes or a consistent problem-details/error model, including stable error codes and correlation IDs.

Support pagination, sorting, filtering and bounded page sizes for list endpoints.

Use explicit DTOs; do not expose persistence entities or internal database structure.

Define validation rules, field formats, nullability, enum values, date/time zones and decimal precision in API contracts.

Use idempotency keys or equivalent controls for operations where duplicate requests could create duplicate submissions, payments/financial side effects or workflow actions.

Define concurrency handling for updates and approvals, such as version fields/ETags or equivalent optimistic locking.

Use secure CORS allowlists for the separately hosted React application; never use permissive wildcard CORS with credentials.

Provide consistent file upload/download APIs with authorization, content-type validation, size limits and secure storage references.

Expose configuration APIs for themes, branding, feature flags, workflow definitions, business rules, permissions and notification templates.

Avoid UI-specific response coupling; API contracts must serve React and approved future clients.

29.2 Authentication and Frontend Integration

OPEN DECISION: approve the identity model (bank SSO/OIDC/SAML, OAuth2/OIDC authorization server, or other enterprise identity provider), token/session handling, MFA, logout, refresh, service-to-service authentication and identity federation. Do not invent a production identity provider.

The React frontend shall not contain database credentials, SMTP credentials, encryption keys or privileged service secrets.

Backend authorization remains authoritative even when the frontend receives permission metadata for rendering.

The API shall provide the authenticated user's safe profile, institution context, effective permissions and feature capabilities.

Document browser security controls including CSP, secure cookies/token storage approach, CSRF protection where cookie-based authentication is used, XSS prevention and secure file handling.

Support separate frontend and backend deployment origins with controlled CORS and environment configuration.

30. Security, Privacy and Banking Control Requirements

The product is intended for banks. Security controls must be treated as release requirements, not optional enhancements. Final controls and assurance evidence must be agreed with each target bank's security, risk and compliance teams.

Enforce TLS for all network traffic and approved encryption at rest for databases, backups, object/file storage and secrets.

Use strong authentication, MFA and enterprise SSO integration where required by the bank.

Enforce least privilege, institution isolation, server-side authorization and segregation of duties.

Protect against common web/API risks including injection, broken access control, insecure direct object references, SSRF, XSS, CSRF where applicable, insecure file upload, mass assignment and excessive data exposure.

Apply secure password handling only if local passwords are supported; use a modern adaptive password hashing algorithm and policy approved by security owners.

Apply rate limiting, account/session controls, secure headers, secure cookie settings and brute-force protections as appropriate.

Mask sensitive personal, vendor and financial data in logs, error responses and audit payloads.

Support configurable data retention and secure deletion subject to legal hold and banking policy.

Maintain dependency vulnerability scanning, secure build pipeline, code review, secrets scanning and software composition analysis.

Define backup, disaster recovery, RPO/RTO, incident response and security monitoring requirements with the bank.

Support integration with bank SIEM/log management where required.

Conduct threat modelling and penetration testing before production deployment.

No certification (for example ISO 27001, PCI DSS or other regulatory compliance) shall be claimed unless independently achieved and applicable to the deployment. Applicable jurisdictional banking, privacy and data-residency requirements must be confirmed with each bank.

31. Document Management and Attachment Security

Support controlled upload, download, preview where safe, metadata management and association of documents with OPEX/CAPEX requests and approval events.

Store file metadata separately from file bytes; use approved private object storage or secured file storage rather than public web directories.

Use opaque storage keys and authorized download endpoints; never expose predictable public file paths.

Validate extension, MIME type, file signature, size and filename; scan uploaded files for malware where available.

Apply tenant isolation and record-level authorization to every document operation.

Support retention, archive, replacement/version history and deletion policy according to bank requirements.

Encrypt stored documents and transfer them over TLS.

Audit uploads, downloads, replacements and deletion attempts without logging document contents.

32. Integration and Master Data Administration

The legacy product depends on shared ApplicationPanel user, department and branch master data. The target product shall not hardwire itself to that legacy database.

Define canonical internal master-data models for institutions, users, departments, branches/business units, designations, vendors and currencies as applicable.

Support controlled manual administration and/or integration adapters for bank-approved HR, directory, ERP, vendor and finance master sources.

External integration must be configurable per institution and isolated behind adapter interfaces.

Support secure credential references, endpoint configuration, connection testing, timeout/retry policies, error monitoring and integration audit.

Define source-of-truth and conflict-resolution rules for each synchronized master-data domain.

No live ERP, core banking, GL or HR integration is included as a confirmed legacy feature; each integration requires a separate interface specification and approval.

33. Reporting, Export and Data Governance Expansion

Retain the documented OPEX/CAPEX operational and management reports, Excel export and audit reporting.

Provide institution-scoped report access and field-level masking where required.

Use asynchronous report generation for large exports, with expiry, secure download and audit.

Apply export row limits, pagination or asynchronous jobs according to approved operational thresholds.

Define report definitions, KPI formulas, currency conversion basis, time zone and treatment of cancelled/rejected/reverted requests.

41. Important Implementation Guardrails

Do not implement the React frontend as JSP or embed frontend pages inside the Spring Boot application. The target frontend is a separate React application.

Do not hardcode institution names, logos, colors, roles, approval limits, workflow routes, email content or institution-specific business rules.

Do not store mail credentials or other secrets in plaintext, source control, browser storage, application logs or audit payloads.

Do not execute arbitrary scripts or SQL entered by administrators as workflow/business rules or email templates.

Do not let configuration changes rewrite the approval path of an already submitted request without an explicit approved migration/reassignment process.

Do not rely on frontend visibility for security; every API and resource access must be authorized on the backend.

Do not assume that all banks have the same organizational hierarchy, departments, currencies, approval roles or email infrastructure.

Do not claim compliance certifications or bank regulatory approval without evidence and formal sign-off.

Do not mark existing functionality as implemented or verified without reviewing the actual repository, tests and deployment evidence.
