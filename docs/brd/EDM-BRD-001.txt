1. Executive Summary
The Expense Delegation Matrix (EDM) is a configuration-driven expense request, delegation and approval platform for Head Office Operating Expenditure (OPEX) and Capital Expenditure (CAPEX). Administrators configure categories, sub-categories, delegation rules, recommending authorities, Expense Committee (EC) levels, currencies and approval limits. Requesters then submit expenses; the system determines the approval route from the configured rules rather than asking the requester to choose approvers.
The reference implementation is an ASP.NET Web Forms application backed by Microsoft SQL Server stored procedures and shared Albaraka/ApplicationPanel master data. The proposed rebuild will implement the documented business capabilities on Java Spring Boot, PostgreSQL and JSP. The rebuild is intended to reduce database-procedure coupling, improve maintainability and make the product reusable for multiple client institutions.
The reference document describes 13 functional modules, OPEX and CAPEX form field maps, 46 OPEX save parameters, 57 CAPEX save parameters, approval workflows, reporting, configuration audit trails and several known gaps. The BRD treats those findings as the functional baseline and separately labels target-product proposals.
2. Business Context and Problem Statement
2.1 Current Situation
•	The existing EDM is implemented in .NET / ASP.NET Web Forms and Microsoft SQL Server.
•	A significant amount of behaviour is implemented in stored procedures and direct database queries, making business flow difficult to maintain and evolve in the application layer.
•	The current implementation depends on shared ApplicationPanel user, department and branch data.
•	The supplied reference records inconsistent/legacy table usage, unclear workflow combinations, incomplete role-based access checks and undocumented deployment/NFR details.
•	The current application is reported by the requester as unstable and difficult to maintain; this operational assessment is requester-provided context, not a measured finding in the reference specification.
2.2 Business Problem
The business needs a stable, auditable and configurable workflow product that can enforce expense delegation consistently across OPEX and CAPEX without rebuilding client-specific logic for each bank or institution.
2.3 Desired Business Outcome
•	A maintainable application-layer workflow engine with database persistence and integrity constraints.
•	Central administration of approval routing and financial thresholds.
•	Consistent request, approval, revert, resubmission and reporting experiences.
•	Tenant/client-specific branding and business configuration without code changes for ordinary configuration differences.
•	Clear traceability for every request, approval action, configuration change and notification.

6.1 Navigation Behaviour
•	OPEX submission returns the user to the OPEX register.
•	CAPEX submission returns the user to the CAPEX register.
•	Register rows open the relevant approval/view page.
•	A reverted request opens in editable mode for its creator in My Request or designated recipient in My Approvals; other users see the read-only approval view.
•	Reporting detail links open the relevant OPEX or CAPEX approval/detail page.
•	Register default date filter is the previous 30 days through today.
7. End-to-End Business Processes
7.1 OPEX Request Lifecycle
1.	Requester opens OPEX form; system pre-fills requester, department, date and reference.
2.	Requester enters expense classification, vendor, currency, amounts, allocations, invoices, business flags and justification.
3.	Requester completes required-document checklist and uploads supporting documents.
4.	System validates required values, invoice/approval amount equality, positive amount, justification and conditional attachments.
5.	System saves request and resolves the approval route from active configuration.
6.	Requester tracks the request in My Request; approvers see assigned items in My Approvals.
7.	If returned, the creator or designated revert recipient corrects and resubmits under the applicable workflow path.
7.2 CAPEX Request Lifecycle
8.	Eligible department user opens CAPEX form; new-request access is limited to Admin, Information Technology and Digital in the reference implementation.
9.	Requester enters category/sub-category, vendor, currency, amount, tax, payment terms, finance fields, asset-book allocations, item-wise details and budget information.
10.	System validates invoice total, approval amount and charge total; requires item-wise details and valid warranty date.
11.	Requester completes checklist and attaches required documents.
12.	System saves request and routes it through the configured CAPEX workflow.
13.	If routing fails after save, the legacy application deletes the request; the new design must instead use an atomic transaction so incomplete requests are not committed. (Target proposal)
14.	Returned CAPEX requests can be corrected and resubmitted when eligible.
7.3 Approval Processing
15.	Approver opens an assigned request; request details are read-only.
16.	System verifies that the user has a pending approval at the current workflow step and has not already acted at that step.
17.	Action panel is displayed only when assignment, status and workflow rules permit it.
18.	Approver selects an available action. Remarks are required for approve, reject and revert; forward requires a recipient and remarks.
19.	System records the action, updates workflow progress/status and triggers applicable email notification.
20.	EC progress is calculated using the configured quorum and any required CEO/CFO participation.
7.4 Revert and Resubmission
•	A revert action requires remarks/comments.
•	An EC-stage revert returns the request to the last Phase-1 approver.
•	The requester sees the reverted request in My Request and can edit it.
•	In My Approvals, only the designated revert recipient receives editable access; other approvers receive read-only view.
•	Selective revert to a chosen previous approver is supported for eligible requests; eligibility criteria remain an open decision.
•	Workflow resume and Phase-2 resubmission are separate documented operations in the legacy implementation; the exact target state machine must be approved.

8.2 OPEX-Specific Requirements
•	Non-recurring expenses require expenditure justification.
•	Quotation 1 is always required. Quotations 2 and 3 are required when Three Quotations Attached is selected; otherwise comments are required for missing optional quotations.
•	Already Approved requires an approved-document attachment.
•	Tax-exemption and GRN documents are required when their respective options are selected.
•	OPEX captures accrued amount, amount, last approved amount, YTD and MTD expenses, recurring status, budgeted/unbudgeted flags and term of payment.
•	OPEX captures previous expense summary rows and branch / Head Office charge allocations.
•	OPEX supports add-vendor modal through the department vendor capability; the exact OPEX modal field map is not separately supplied.
8.3 CAPEX-Specific Requirements
•	New CAPEX requests are restricted to Admin, Information Technology and Digital departments in the reference implementation; the target must make this an institution configuration, not a code constant.
•	Category and sub-category are required; selecting Other requires CategoryOther and/or SubcategoryOther.
•	Request type and Sales Tax Authority selection are required.
•	Invoice total, approval amount and total charges must be positive and equal.
•	Item-wise details are mandatory before proceeding.
•	Warranty date cannot be in the past.
•	Unbudgeted or over-budget requests require a reason of at most 500 characters.
•	CAPEX captures purchase nature, warranty, finance date/comment, budget comments, terms and conditions, asset classification flags and values.
•	CAPEX item-wise rows include actual and budget rates/units/amounts and system-calculated variances; exact formulas are not documented.
8.4 Register Requirements
•	Each register shall provide My Request and My Approvals views.
•	Search/filter by reference, expense/request type, status, date range and Head Office/branch or department.
•	Default date range is previous 30 days through current date.
•	Data must be scoped to the authenticated user's permitted visibility.
•	Returned request edit destination depends on creator or designated revert-recipient identity.
•	Excel export is supported for filtered results.
•	Print/PDF is available only for qualifying approved requests in My Request; exact eligibility conditions are open.
8.5 Approval Requirements
•	Approval pages display request details read-only, allocations, checklist, attachments and milestone/history.
•	Actions are visible only for a valid pending assignment and current workflow state.
•	Approve, reject and revert require remarks; forward requires a selected recipient and remarks.
•	EC users may approve, reject or revert when assigned and pending; an EC user cannot act twice at the same step.
•	CEO may approve or revert but cannot reject an EC request.
•	EC revert requires comments and routes back to the last Phase-1 approver.
•	EC section is hidden when there is no applicable EC workflow, including department-head-limit and superseded workflows.

10. Approval and Delegation Framework
10.1 Documented High-Level Route
The documented normal route is: Request Submission → Department Head / Unit Head (Phase 1) → Recommending Authority (where configured) → Expense Committee level(s) (Phase 2), with CEO and/or CFO participation when configured.
10.2 Department Head Limit
•	Approval amount at or below the configured General Delegation limit routes to the Department Head only (Phase 1).
•	Approval amount above the limit proceeds through Phase 1 and then the configured later approval route.
•	Legacy helper default is PKR 20,000 when no configured limit is available.
10.3 EC Levels and Quorum
•	EC levels have configured amount ranges, selected members, required EC member count and minimum approval count.
•	The reference narrative describes Levels 1–3 as descending approval intensity; exact amount boundaries and relationship to configurable EC levels are not verified.
•	Required CEO/CFO participation is configured at EC level; CEO cannot reject. CFO action restrictions need confirmation.
10.4 Standalone Approvals
Standalone CEO and Head of Admin & GST (HOD) routing, and CEO/CFO standalone approval limits, are described in the product narrative. Their precise sequence, limits, interaction with EC levels and action permissions are not sufficiently defined. These must not be implemented by assumption.
10.5 Approval State Machine
The source names Pending, Approve, Reject, Revert and Forward; CAPEX also uses Submitted. The complete state machine, terminal statuses, allowed transitions, cancellation/deletion policy and concurrency behaviour are not supplied. A formally approved state-transition matrix is a release prerequisite.
Action	Documented Permission / Constraint
Approve	Unit Head and assigned EC member; CEO can approve. Remarks required.
Forward	Unit Head; recipient required and remarks required. EC/CEO forward permissions not stated.
Reject	Unit Head and EC member; CEO cannot reject EC request. Remarks required.
Revert	Unit Head, EC member and CEO as described; remarks/comments required. EC revert returns to last Phase-1 approver.
Edit / Resubmit	Creator from My Request or designated revert recipient from My Approvals for returned requests.

13. Security and Access Control
The reference implementation has authentication/session checks in many pages but does not establish a complete role-based permission model. Some configuration pages have no role check in page source. The reporting module hard-codes every signed-in user as Finance_Admin and disables intended role checks. This is a material control gap.
13.1 Target Requirements
•	Require authenticated access to all application pages and server endpoints.
•	Enforce authorization on the server for every operation; hiding a JSP button is not an authorization control.
•	Define institution-configurable roles and permissions for request creation, viewing, approval, configuration, reporting, audit viewing and export.
•	Enforce record-level access: requester ownership, current workflow assignment, designated revert recipient, department restrictions and tenant boundary.
•	Prevent duplicate or replayed approval actions through transactional state checks.
•	Protect vendor CNIC, NTN, STRN, contact number and address according to the client's security/privacy policy.
•	Never log passwords, authentication tokens, full sensitive identifiers or document contents.
•	Define session timeout, password/SSO policy, encryption, retention and backup requirements with the client security team.
These security controls are target proposals and must be approved by the bank/client security stakeholders; the reference document does not provide encryption, masking, retention or certification requirements.

15. Target Solution and Configuration Requirements
15.1 Target Technology
Layer	Target
Web UI	JSP server-rendered embedded UI; reusable layouts, tags/fragments and client-side enhancement only where useful.
Application	Java Spring Boot modular monolith initially; controllers, application services, domain services, repositories and integration adapters.
Persistence	PostgreSQL with normalized relational model, foreign keys, unique constraints and database migrations.

15.2 Architecture Principles
•	Keep business rules and workflow decisions in Java domain/application services; use PostgreSQL for persistence, relational integrity, indexes and transactional guarantees.
•	Do not reproduce the legacy stored-procedure architecture one-for-one. Reimplement the business behaviour, not the old technical coupling.
•	Use a modular monolith as the initial deployment shape unless scale or organizational boundaries justify service decomposition.
•	Separate OPEX and CAPEX domain-specific fields while reusing common request lifecycle, attachment, allocation, approval, audit and reporting capabilities where semantics match.
•	Keep client-specific differences in configuration/strategy/adapter layers, not scattered if/else conditions or hard-coded constants.
•	Use database migration scripts (e.g. versioned migrations) as the controlled schema change mechanism.
•	Use DTO validation at request boundaries and domain validation in services; never trust client-side validation alone.
•	Use transactional boundaries around request submission, route creation, approval action, revert and resubmission.
15.3 Multi-Client / Tenant Configuration
The requester explicitly requires a product that can be sold to multiple clients with minimal code changes. The following are target-product requirements, not confirmed features of the legacy Albaraka application.

Do not mix tenant-owned data without a formally approved isolation model.

•	Configuration should be separated into platform-level settings, tenant-level settings and workflow/business settings.
•	Secrets such as database credentials and SMTP passwords must be managed outside ordinary UI configuration and stored in a secure secret store/environment.
