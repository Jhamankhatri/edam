# Database Guidelines (PostgreSQL)

## 1. Ownership of the schema

**Flyway is the only mechanism that changes the schema.** Hibernate runs with `ddl-auto: validate` in every
profile, including `local`. A mapping that disagrees with the migrated schema fails at startup rather than
being silently corrected — that is how mapping drift is caught before it reaches a shared environment.

```
src/main/resources/db/migration/
├── V1__baseline.sql            baseline schema (institution)
└── V2__institution_seed.sql    reference institution (demo-bank)
```

### Migration rules

| Rule | Reason |
|---|---|
| Never edit an applied migration | Flyway checksums protect history; editing rewrites a shared past |
| One logical change per version | Reviewable, revertible |
| `V<n>__<snake_case_description>.sql` | Predictable ordering, no ambiguity |
| Forward-only; no `down` scripts | Roll-forward is the operational model for a banking product |
| `baseline-on-migrate: false`, `out-of-order: false`, `validate-on-migrate: true` | An unexpected or non-linear schema must stop the deployment |
| No `CREATE EXTENSION` without an ADR | Extensions need DBA and hosting approval |
| Reference/**seed** data only in migrations | Client business data is never seeded by a migration |

A destructive change is a two-release operation: add the new structure, migrate and dual-write, then drop
the old structure in a later release after the business confirms no consumer remains.

## 2. Naming and types

| Concern | Convention |
|---|---|
| Identifiers | `snake_case`, singular table names (`institution`, not `institutions`) |
| Primary key | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| Foreign key | `<referenced_table>_id`, with an explicit `CONSTRAINT fk_<child>_<parent>` name |
| Unique | `CONSTRAINT uk_<table>_<columns>` |
| Check | `CONSTRAINT ck_<table>_<rule>` |
| Index | `ix_<table>_<columns>` |
| Boolean | `NOT NULL DEFAULT` explicit; never nullable booleans |
| Timestamps | `TIMESTAMPTZ`, stored in UTC; presentation converts to the institution's zone |
| Money | `NUMERIC(19,2)` — never `float`/`double` |
| Rates | `NUMERIC(19,6)` |
| Codes | `VARCHAR(n)` with a `CHECK` for format (`^[A-Z]{3}$` for ISO-4217) where the format is contractual |
| Enumerations | `VARCHAR` + `CHECK (col IN (...))` until the value set is stable; a lookup table once it becomes configurable |

Every table carries `COMMENT ON TABLE`/`COMMENT ON COLUMN` where the business meaning is not obvious — the
database outlives the developer who wrote it.

## 3. Constraints are not optional

The database is the last line of defence for integrity; application validation is for user experience, not
correctness.

* **Primary key** on every table.
* **Foreign key** on every relationship, with an explicit `ON DELETE` behaviour (`RESTRICT` by default —
  the BRD requires delete guards, e.g. a category with sub-categories cannot be deleted).
* **Unique constraints** for business keys. Where "unique among active rows" is required (e.g. active
  category name), use a partial unique index: `CREATE UNIQUE INDEX ... WHERE active`.
* **CHECK constraints** for invariants that must hold forever: positive amounts, `lower_bound < upper_bound`,
  colour format, ISO currency format, mutually exclusive flags.
* **NOT NULL** for anything genuinely mandatory. A nullable column must represent a real business state
  ("not configured"), not laziness — see `institution.department_head_limit`, which is nullable because
  "no threshold configured" differs from zero.

## 4. Auditing

All mutable tables inherit the audit contract:

| Column | Type | Populated by |
|---|---|---|
| `created_at` | `TIMESTAMPTZ NOT NULL` | JPA auditing (`@CreatedDate`) |
| `created_by` | `VARCHAR(64) NOT NULL` | `AuditorAware` → employee ID, or `system` |
| `updated_at` | `TIMESTAMPTZ NOT NULL` | JPA auditing (`@LastModifiedDate`) |
| `updated_by` | `VARCHAR(64) NOT NULL` | `AuditorAware` |
| `version` | `BIGINT NOT NULL DEFAULT 0` | JPA `@Version` (optimistic locking) |

`AuditableEntity` is the single `@MappedSuperclass` in the codebase. It exists because repeating six columns
on every table invites drift; it contains no business behaviour and must never gain any.

**Business audit** (who approved what, old/new configuration values, IP address) is a separate, append-only
event store delivered in a later phase. `created_by`/`updated_by` answer "who last touched this row"; they
do not replace a full audit trail, and they must not be presented as one.

## 5. Indexing

Index for the queries the application actually issues, not speculatively.

* Every foreign key gets an index unless it is already the leading column of another index — PostgreSQL does
  **not** create one automatically, and a missing FK index becomes a lock-contention problem on delete.
* Partial indexes for "active only" lookups: `CREATE INDEX ix_institution_active ON institution (code) WHERE active;`
* Composite indexes follow the query's column order (equality columns first, then range).
* Reporting queries get covering/index-only indexes only after the query and its data volume are known.
* Every index is justified in the migration comment: which query it serves.

## 6. Transactions

* **Service-level boundaries.** `@Transactional` lives on application services, not controllers or
  repositories. `@Transactional(readOnly = true)` is the class default for query services and is overridden
  per method for writes.
* **One transaction per business operation.** Creating a request, its child rows, its resolved route and its
  audit event must commit or roll back together (BRD §7.2 step 13, FR-REQ-010). The legacy application
  deleted requests when routing failed after save; the target design must never persist a half-built request.
* **Optimistic locking is mandatory** on aggregates that two actors can change concurrently (approvals,
  configuration). A clash surfaces as `EDAM-3002` / HTTP 409 and the user reloads.
* **No long-running transactions** across external calls (email, file storage). Those go through an outbox
  in a later phase.
* **`open-in-view: false`.** Lazy loading outside the service boundary is a bug, not a feature; JSPs receive
  view models, never entities.

## 7. Multi-institution (tenant) data

**No tenant-owned table exists in this phase** — the isolation model is an open decision (OD-20, ADR-0002).
Do not add a tenant column, a Hibernate tenant filter or schema routing until that ADR is superseded.

When it is:

* Every tenant-owned table carries the approved discriminator (`institution_id` for shared-schema, or the
  schema/database boundary for the isolated models).
* The discriminator is set by the platform, never by request input.
* Every query is either generated through a repository whose tenant predicate is enforced centrally, or went
  through review proving the predicate is present. A missing predicate is a data breach (AC-12).
* Tenant-owned tables reference `institution(id)` with `ON DELETE RESTRICT`.
* Cross-tenant reporting is an explicitly authorized, audited operation — not a missing `WHERE` clause.

## 8. What must not appear in the database

* **Business rules in stored procedures, triggers or functions.** The BRD requires rules in the application
  layer so they are testable, reviewable and version-controlled with the code. Format/range checks in
  `CHECK` constraints are integrity, not business logic.
* Full-text duplication of application logic (e.g. a trigger that re-implements approval routing).
* Credentials, tokens or secrets in any column. Integration secrets belong in a secret manager.
* Sensitive identifiers (CNIC, NTN, STRN, account numbers) in plain text without an approved protection
  decision (BRD §13.1) — the column exists only when that decision is made.
* Denormalised "current status" columns that can disagree with the workflow history. Status is derived or
  maintained transactionally with the transition record.

## 9. Schema evolution checklist for a new table

1. Does the table belong to an approved phase? (No OPEX/CAPEX tables in the foundation.)
2. Does it inherit the audit contract and `version`?
3. Primary key, foreign keys with `ON DELETE`, unique business keys, CHECK invariants?
4. Indexes for each known query — and a comment naming the query?
5. Is money `NUMERIC(19,2)` and are rates `NUMERIC(19,6)`?
6. Is the entity mapping (`@Table`, `@Column(name/length/precision/scale/nullable)`) exactly aligned so
   `ddl-auto: validate` passes?
7. Does a migration test prove it applies to a clean database (`mvn verify` with Testcontainers)?
8. Is tenant ownership decided and consistent with ADR-0002?
